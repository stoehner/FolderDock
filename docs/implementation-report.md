# FolderDock — Implementation Report

Date: 2026-10-17 (v1.0.0) · Windows 11, x64

> **Revised 2026-10-31 (v1.3.9):** the drag model section and the deviation list were updated to current behavior, which changed after v1.0.0 — most notably in **v1.3.7 (2026-10-21/27)**, when drag-out became a move and imports moved sources in. Test and deliverable counts below reflect v1.0.0 as originally delivered; the README carries the current numbers.
>
> **Revised 2026-11-01:** the v1.3.7 drag model was itself replaced. A user-reported bug — a refused drop recycled the library original — proved the `dragend` verdict unusable: Chromium guesses that effect on Windows (crbug 41183574, "we always select 'copy'"), and refusals on this runtime measured `move`, `move` and `copy`. Every file drag now rides the native OS carrier and retirement happens only on settled disk truth. The "Drag model" section and deviations 2 and 10 were rewritten for this; the v1.3.7 wording survives only as history.

## Stack

Electron 44 + React 19 + TypeScript 6 (strict) + Vite 8 via electron-vite 6, Tailwind CSS 4 (utilities + preflight) with the prototype's hand-ported CSS for visual fidelity, zustand 5 for state, chokidar 5 for filesystem watching, marked + DOMPurify for sanitized Markdown, pdfjs-dist 6 for PDF rendering, Playwright 1.64 for Electron E2E, Vitest 5 for unit tests, electron-builder 26 for packaging (NSIS + portable).

## Architecture

- `src/main` — owns everything filesystem: root resolution (`Documents\FolderDock` default, `FOLDERDOCK_ROOT` env or Settings override), scanning (one directory level = one collection; loose root files surface as a virtual **Unsorted** collection), file ops (create/rename/move/delete/import/write), atomic text writes (`*.fdtmp` temp + rename), mtime conflict detection, chokidar watcher (debounced → `library:changed`), native drag (`webContents.startDrag` with per-type PNG icons generated at build time by `scripts/gen-icons.mjs`), JSON prefs store in `%APPDATA%`, `fdfile://` protocol restricted to the library root.
- `src/preload` — minimal allowlisted typed bridge (`contextBridge`), `sandbox: true`; `webUtils.getPathForFile` for Explorer drop paths.
- `src/renderer` — React port of the prototype: custom frameless titlebar wired to real window controls, toolbar/search/filters, glass folder cards with individually draggable sheets (0/1/2/3 sheet variants preserved), inside file list, fixed-position context menus, modal system (new folder with art swatches, renames, confirm, move, help, settings), editor with Edit/Preview tabs, side preview (Markdown/text/image/PDF), 250 ms hover summaries with excerpt/meta caches.
- `src/shared` — types, kind detection, excerpt extraction, prefs validation — pure, unit-tested code shared by both processes.

## Drag model (design decision)

**Current (disk-truth carrier, 2026-11-01).** Every file drag — a single paper sheet or file row, or Ctrl-selected rows — hands the real file to the native main-process carrier (`webContents.startDrag`); no HTML5 drag session starts and no `dragend` logic remains:

- A renderer event cannot report the OS drag outcome on this stack: native drags never report it (probed 2026-10-27), and the HTML5 fallback's `dragend` verdict proved a guess on Windows — refused drops measured `move`, `move` and `copy` (a value FolderDock never writes anywhere), while Chromium confirms "we always select 'copy'" for its `dragend` heuristics (crbug 41183574). No event ever decides a recycle.
- The carrier itself can only deliver copies: Electron's `DragFileItems` starts the OLE drag with allowed operations `DRAG_COPY | DRAG_LINK` (`drag_util_views.cc` line 47, v44.10.1) and `webContents.startDrag` accepts only `file`/`files`/`icon` — no parameter can add `DRAG_MOVE`, so Explorer delivers a copy on every target, same drive or not (reported from daily use 2026-11-01, root-caused 2026-11-02). After a single-file drag starts, a settle scan chain asks disk truth: first scan at 1.2 s, step scans every 4 s, at most 3 scans (~10 s window). A scan that finds the file gone from the library root and its name listed nowhere in the library means Windows really moved it away (a Recycle-bin target, or a future carrier that offers move): the scan snapshot is applied and a toast reports `"name" moved out of the library`. A scan that still finds it — the copy Electron delivers, a refused drop, Esc, Alt-drag shortcut — leaves a verdict the disk cannot separate, so the user's declared intent resolves it at the settle cap: plain drag = keep with one educational toast naming the Shift gesture; Ctrl/Alt or a multi-selection drag = silent keep (explicit copy/shortcut intent); Shift = confirm modal whose own confirm click recycles the library copy into the Recycle Bin with the `"name" moved out of the library` toast. No settle verdict ever recycles on a guess. A scan that finds the basename re-homed in another collection stops quietly; dropping a file back onto any FolderDock surface now rides the import path, which has its own toasts.
- Multi-selection drags keep copy semantics: the targets receive copies and the originals stay.
- Drop-in from Explorer, dialog imports, and drops back onto FolderDock surfaces all behave like ordinary OS file drops (there is no internal drag marker anymore): same-drive sources rename into the collection, cross-drive sources copy in and the source is recycled (copy fallback if recycling fails), byte-identical duplicates are skipped with an explanation, name collisions get ` (2)` suffixes, and a library file dropped on the shelf background stays put with a hint toast.

**History.** v1.0.0 (2026-10-17) shipped every drag as a native copy-out (originals always left in place). v1.3.7 (2026-10-21/27) moved drag-out to an HTML5 `DownloadURL` carrier plus a `dragend` outcome gate plus a settle-window recycle of the original, to stop drag-out + import-back from multiplying copies. On 2026-11-01 a refused drop recycling the original was reported and root-caused with instrumented trials; the verdict values above (and Chromium's own account of guessing `dragend.dropEffect`) killed that carrier, and the disk-truth model above replaced it. That same evening, daily use exposed the model's blind half: drag-out to the Desktop left a copy inside the library, because Electron's carrier offers Windows copy | link only (`DragFileItems`, `drag_util_views.cc` line 47) — Windows never moves a file out of an Electron app source, so "same-drive drops default to move" held for Explorer sources only. v1.3.11 (2026-11-02) replaced that premise with declared intent: plain drags keep with one educational toast, Ctrl/Alt/multi keep silently, and a Shift drag gets a confirm modal whose own click is the only party that recycles the library copy (Recycle Bin, recoverable).

## Deviations from the handoff / prototype

1. **Simulated external drop zone removed**, as instructed once native drag-out was implemented.
2. **Drag imagery** is a colored type icon (from `resources/drag/*.png`) rather than a live thumbnail; `startDrag` only accepts image assets and generating faithful per-file thumbnails would require an image-processing dependency. Documented as a limitation. Since 2026-11-01 this applies to every file drag again: single- and multi-file drags all run the native `startDrag` carrier with a per-type icon (as in v1.0.0); no HTML5 carrier remains for Chromium to style.
3. **Import semantics** (unchanged at v1.0.0: Explorer drag-in and dialog import **copied**, originals untouched). Since v1.3.7 (2026-10-21/27) imports **move** the source into the library — same drive: renamed in place; other drive: copied and the source recycled (fallback to copy if recycling fails) — with byte-identical duplicates skipped and ` (2)` collision suffixes. The prototype's "files added to the selected collection" toast pattern is kept.
4. **Full-screen drop overlay replaced** with a slim bottom hint bar plus per-card glow — the overlay obscured the drop targets themselves.
5. **Side preview** docks to the right edge below the titlebar; on narrow windows (<1020 px) it overlays the shelf, and the window auto-widens once (up to 1040 px) when opened if the work area allows. The prototype floated the panel outside the mock window, which isn't possible inside a real window.
6. **Root-level loose files** are exposed via a virtual *Unsorted* collection (the prototype had no equivalent); the name is reserved against real folder creation.
7. **Deletes go to the Recycle Bin** (`shell.trashItem`) rather than hard-deleting — safer than the prototype's hard removal.
8. **Nested subdirectories** inside a collection are not displayed (flat collection model, matching the prototype's card list). Files in them are untouched and invisible in the UI.
9. The prototype's fake window buttons (minimize/maximize/close/reset-to-demo) became real window controls; "reset" was a demo-only concept.
10. **Drag-out retires the original only on disk truth (since 2026-11-01) — revised deviation from the handoff.** The handoff required that dragging a file to an external target must not delete or move the original, and prohibited HTML5 carriers. v1.3.7 (2026-10-27) satisfied the no-loss goal but violated the carrier prohibition with an HTML5 `DownloadURL` carrier plus a `dragend` outcome gate. On 2026-11-01 a user-visible bug proved that gate unsafe: an app that refused the drop recycled the original because `dragend` reported non-`none` effects (`move`, `move`, `copy`) for refusals — Chromium engineers confirm the `dragend` effect is a Windows guess ("we always select 'copy'", crbug 41183574). The HTML5 path, the `dragend` gate and the post-drag force-recycle are fully removed; all drags run the native `startDrag` carrier (no carrier violation anymore) and the library retires an entry only when a settle scan proves Windows actually moved the file away. Refused, cancelled, shortcut and copy deliveries keep the original by construction — a stronger guarantee than the handoff's. Plain drag-out keeps the original with an educational toast: Windows delivers a copy (the carrier offers copy | link only), so move-out now requires Shift plus a confirm modal — see Deviation 11.

11. **Move-out on drag is user intent, not carrier behavior (since 2026-11-02).** Daily use right after v1.3.10 showed the disk-truth model's other half: dropping onto the Desktop left a copy inside the library, meanwhile silently. Root cause, upstream: Electron's `DragFileItems` starts the OLE drag with allowed operations `DRAG_COPY | DRAG_LINK` (`shell/browser/ui/drag_util_views.cc` line 47, v44.10.1) and `webContents.startDrag` accepts only `file`/`files`/`icon` — no API surface exists to add `DRAG_MOVE`, so Windows never moves a file out of an Electron app source; the earlier "same-drive Desktop/folder drops default to move" wording describes Explorer-to-Explorer drags only. Drag intent now resolves the kept verdict at the settle cap, because the disk cannot separate "copy delivered" from "refused/cancelled": a plain drag keeps with one educational toast naming the Shift gesture; Ctrl, Alt, or a multi-selection drag keeps silently (explicit copy/shortcut intent); a Shift drag — a move request — opens a confirm modal (`Move out of the library?`) whose confirm recycles the library copy into the Recycle Bin and reports the same `"name" moved out of the library` toast. No settle verdict recycles anything on a guess, and a scan that proves a real move-away (a Recycle-bin target, or a future carrier that offers move) still wins without the modal.

## Limits & known constraints

- Editor: text/Markdown up to 2 MB, UTF-8 (BOM preserved; other encodings are not transcoded). NUL-bearing content is treated as binary — preview/edit disabled, reveal/open offered instead.
- Preview caps: PDF 30 MB and first 40 pages; import 200 MB per file.
- External concurrent modification is detected via mtime at save time (overwrite / reload-from-disk choice); watcher-based re-validation between keystrokes is not attempted.
- Drag-out: the Electron carrier can only deliver copies (copy | link OLE mask, `drag_util_views.cc` line 47; no move offered), so every external drop lands as a copy and the library original always survives the settle scans. Move-out is user intent: a Shift drag plus a confirm modal recycles the library copy (Recycle Bin, recoverable); plain drags keep with an educational toast; Ctrl/Alt/multi keep silently. Drop targets that only accept non-file content still refuse the drop, and nothing recycles the library original without the user's own click.
- Binaries are unsigned — SmartScreen shows a warning on first run.
- The diagnostics ledger (v1.3.12) is local-only by construction: `main.log` in `%APPDATA%\FolderDock\logs` (1 MB rotation into `main.1.log`), `hang-snapshot.json` written from the window's `unresponsive` event, and `crashReporter` initialized with an empty `submitURL` and `uploadToServer: false`. There is no telemetry, no metrics, and no network endpoint anywhere in the diagnostics path — the ledger is readable only from this machine (Settings → Diagnostics → Open logs / Copy diagnostics). Honest caveat: the ledger records what the app can observe from main, the renderer, and Electron's own surfaces; a freeze that surfaces in none of them can still pass unlogged — the 2026-11-02 daily-use freeze is that case as of today, and the ledger exists to catch the next one with evidence.
- The NSIS install is per-user; it self-updates from GitHub Releases (the "no auto-updater" line described v1.0.0 and is superseded).
- npm audit reports 8 moderate advisories, all transitive in electron-builder's tooling chain (NSIS signing tools); none affect the shipped runtime.
